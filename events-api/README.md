# Events API — практична робота 4

## Запуск

```bash
cd events-api
npm install
npm start
```

Наявні назви файлів збережено. Налаштування зчитуються з `events-api/.env`, приклад — `.env.example`. `.env` виключений із Git.

| Змінна | Значення | Правила |
| --- | --- | --- |
| PORT | 3000 | Ціле число від 1 до 65535 |
| NODE_ENV | development | development, test або production |
| LOG_LEVEL | debug | debug, info, warn або error |
| MAX_EVENTS | 100 | Додатне ціле число |

`config/env.js` перевіряє конфігурацію через Zod і перетворює числові значення. Некоректна конфігурація зупиняє запуск із кодом 1. Застосунок використовує перевірений об’єкт `env`. LOG_LEVEL перевіряється та доступний для подальшого налаштування логування.

## Маршрути й валідація

| Метод | URL | Результат |
| --- | --- | --- |
| GET | /api/events | Список подій, 200 |
| GET | /api/events?title=JavaScript | Пошук за частиною назви без урахування регістру, 200 |
| GET | /api/events/:id | Подія, 200 |
| POST | /api/events | Створення, 201 |
| PATCH | /api/events/:id | Часткове оновлення, 200 |
| DELETE | /api/events/:id | Видалення, 204 |
| GET | /api/events/error/test | Навмисна помилка, 500 |

Дані `/api/events` зберігаються в масиві та скидаються після перезапуску. Початкова подія має id 1. Старі GET/POST `/api/events-from-file` залишені; POST також перевіряється схемою створення.

`schemas/event.schemas.js` містить схеми Zod:

- title: рядок 3–100 символів після видалення пробілів на краях;
- date: рядок у форматі YYYY-MM-DD;
- description: необов’язковий рядок до 500 символів;
- isOnline: boolean, для POST стандартне значення false;
- id: перетворюється на додатне ціле число;
- query: дозволено лише необов’язковий непорожній title.

Невідомі поля заборонені. PATCH вимагає хоча б одне поле та не змінює непередані поля, зокрема isOnline. Middleware `validate(schema, source)` перевіряє body, params або query та записує перетворені дані назад у запит до основного обробника.

Бізнес-правила перевіряються окремо: відсутня подія — 404 EVENT_NOT_FOUND; однакова назва без урахування регістру та дата — 409 EVENT_ALREADY_EXISTS (також для PATCH); ліміт MAX_EVENTS — 409 EVENT_LIMIT_REACHED.

## Middleware та помилки

Порядок: `requestId → logger → express.json → router → notFound → errorHandler`.

requestId і logger стоять перед маршрутами та JSON-парсером, щоб охоплювати всі запити, включно з некоректним JSON. Кожна відповідь має X-Request-Id. Logger після finish виводить метод, URL, статус, тривалість і requestId. notFound стоїть після маршрутів, оскільки запускається лише коли маршрут не відповів. Error handler останній, має чотири аргументи та обробляє передані через next(error) помилки.

Усі помилки мають Content-Type `application/problem+json` та поля type, title, status, detail, instance, code, requestId. Валідація додає errors із назвами полів і повідомленнями. Некоректний JSON повертає 400 BAD_REQUEST. Помилки 500 не містять stack trace та внутрішніх подробиць; технічні деталі записуються лише в консоль сервера.

## Перевірка

Команди curl, фактичні статуси, заголовки X-Request-Id та JSON-відповіді збережено в [результатах перевірки](events-api/api-results.md). Там є успішна відповідь та приклади помилок 400, 404, 409 і 500. Перевірки використовують окремий порт, щоб не заважати серверу на 3000.
